## Lean Verification Guidelines

This document outlines the workflow for verifying code generated by the `bitc` transpiler.


### 1. Architecture & TCB

All verification adheres to **Total Fuel-Indexed Hoare Logic**.

* **TCB:** Zero axioms. All loops must terminate or hit a `timeout`.
* **Tooling:** Structural proofs and state-passing are automated via `BitcHoare` Aesop ruleset.


### 2. Standard Loop Workflow (Structured CFG)

For standard structured loops, execute the following sequence:

1. **Inject the Invariant:** Every loop requires an explicit invariant `I`.
```lean
apply loopM_hoare (I := fun s => s.regs.x >= 0 ∧ s.regs.y = 2)
```

2. **Structural Reduction:** Invoke the automated solver to handle monadic binds, register modifications, and branch conditions.
```lean
aesop (rule_sets := [BitcHoare])
```

3. **Manual Discharge:** Address remaining mathematical subgoals.
* Use `omega` for linear arithmetic and loop bounds.
* Use `simp_all` or `tauto` for logical tautologies and register equality.


### 3. Irreducible CFGs (State Machine Loops)

Transpiled LLVM IR often produces irreducible control flow (e.g., `goto` spaghetti) modeled as a single loop switching on a `BlockID` or Program Counter (PC). Treat these as state machines.

1. **Define a State-Dependent Invariant:** Do not write monolithic invariants. Map each `BlockID` to its specific precondition using `match`.
```lean
apply loopM_hoare (I := fun s => 
  match s.regs.pc with
  | .entry  => s.regs.x = 0
  | .loop1  => s.regs.x > 0 ∧ s.regs.x < 10
  | .exit   => s.regs.x = 10)
```

2. **Split the State Space:** Before calling `aesop`, force to split the goal into discrete CFG blocks.
```lean
-- Introduce the state and split on the PC/BlockID
intro s hs
cases hpc : s.regs.pc
```

3. **Block-by-Block Reduction:** Once the PC is concretized, apply the standard reduction.
```lean
all_goals {
  simp [hpc] -- Resolve the state dispatcher
  aesop (rule_sets := [BitcHoare])
  omega      -- Or block-specific arithmetic proofs
}
```


### 4. Troubleshooting

If `aesop` fails or hangs:

* **Trace:** Add `set_option trace.aesop true` before the proof to see where the branch fails.
* **Strengthen Invariants:** If a branch cannot be discharged, the invariant is likely too weak to satisfy the postcondition of that specific CFG block.
* **Manual Fallback:** If `aesop` gets stuck on a complex monadic chain, manually apply `seq_hoare` to force the WLP state-passing, then call `aesop` again.


### 5. Rule Set Maintenance

* When adding new `EffectStack` primitives, create a WLP lemma and tag it with `@[aesop safe apply (rule_sets := [BitcHoare])]`.
* **Never** tag lemmas involving loop execution or invariant induction (`loopM_hoare`). These must remain manual injection points to prevent infinite tactic loops.
